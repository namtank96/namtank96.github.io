## 출력 예시

§2 배선 계약이 이 문서에서 가장 값어치 있는 절입니다. "여러 곳"과 "8곳"의 차이입니다.

```markdown
## 2. 배선 계약 (정본 배선 갭 4건)

| # | 계약 | 왜 |
|---|---|---|
| ① | `추천도출()` 에 5번째 분기 추가 — 기존 4개 push 뒤 조건부 | 이게 진짜 드롭인인지의 판정 기준 |
| ② | 분류 enum 을 **8곳 전부**에 동시 추가 (목록 나열) | 한 곳만 넣으면 화면에 안 뜬다 |
| ③ | 하드코딩 배열에 값 추가 (@1601 + @1996 섀도 사본) | 사본이 따로 있어 둘 다 고쳐야 한다 |
| ④ | 해소 플래그 되쓰기 — 루트에서 존중 | 없으면 확정한 건이 다음 실행에 되살아난다 |
```

②의 "8곳"과 ③의 "섀도 사본"은 데모를 만들면서 실제로 세어본 결과입니다.
이 숫자가 없으면 정본 담당이 두 곳쯤 고치고 "왜 안 뜨지"를 하루 붙잡습니다.

§4 토큰 일치는 이렇게 씁니다.

```markdown
## 4. 토큰·클래스 100% 정본 일치

데모 스타일을 정본과 동일하게 씁니다 — 매핑이 아니라 붙여넣기가 되게.
· 토큰: 정본 :root 그대로. 이름 변경 0
· 클래스: 정본 클래스 그대로. demo- 접두 ✕
· 신규 클래스 3개(목록) — 정본에 추가될 것
```

## 이 규칙의 근거

**왜 계약을 먼저 쓰는가.** 데모는 빨리 만들려고 정본과 다르게 짓습니다. 그게 정상입니다.
문제는 데모가 통과한 다음입니다 — "이거 좋네요, 그대로 붙이죠"가 나오는데
그 시점에 이름이 다르고 구조가 다르고 색이 달라서 결국 다시 씁니다.
**다 만든 뒤에 쓰는 계약은 계약이 아니라 회고입니다.**

**왜 배선 지점을 숫자로 세게 하는가.** 같은 값을 여러 곳에서 읽는 구조는
데모에서는 안 보이다가 정본에서 터집니다. 한 곳만 고치면 화면에 안 뜨는데,
에러도 안 납니다. 조용히 없는 것처럼 동작합니다.
**"여러 곳"이라고 적으면 아무 도움이 안 되고, "8곳(목록)"이라고 적으면 체크리스트가 됩니다.**

**왜 섀도 사본을 따로 적는가.** 같은 배열이 두 군데 복사돼 있는 코드는 흔합니다.
하나만 고치면 절반의 경우에만 동작하고, 그 절반이 어느 절반인지 재현이 안 됩니다.
계약서에 위치를 둘 다 적어두면 이 함정을 피합니다.

**왜 교체 경계를 함수 하나로 몰아넣는가.** 경계가 흐릿하면 이식이
"어디까지 바꿔야 하지"를 판단하는 작업이 되고, 그 판단은 매번 다르게 납니다.
**함수 하나 안쪽으로 몰아두면 이식이 판단이 아니라 기계 작업이 됩니다.**

**왜 접두사를 금지하는가.** `demo-` 접두를 붙이면 이식할 때 전부 찾아서 지워야 하고,
지우다 하나 빠뜨리면 스타일이 반쯤 깨집니다. 처음부터 같은 이름을 쓰면 그 작업이 없습니다.
