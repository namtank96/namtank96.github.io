## 출력 예시

기획안 한 건을 돌렸을 때 나오는 형태입니다.

```
## ① 기계 검사
🔴 blocking 1건 / 🟡 경고 3건 / ✅ 통과 12건

  🔴 개수 불일치 — 요약 "적용 사례 5건", 본문 나열 3건.
     둘 중 어느 쪽이 맞는지 확정 전까지 제출 불가.

## ② 판정 — 기계가 못 본 것

| 위치 | 축 | 위반 | 근거 | 권고 |
|---|---|---|---|---|
| §3 도입효과 | 주장 정직성 | "검증 완료"가 정확성으로 읽힘 | 실제로 확인된 것은 동일 입력에 동일 출력이 나온다는 것뿐 | "자기일관성·재현성 확인, 정확성은 현업 검증 필요"로 |
| §4 적용 범위 | 주장 정직성 | "범용"의 축이 불명 | 구조는 공유하나 단계 수가 대상별로 다름 | 어느 축에서 범용인지 명시 |
| §5 기준값 | 도메인 사실성 | 임계값이 그럴듯하나 출처 없음 | 업계 통용 범위와 어긋날 소지 | 값 자체는 두고 `SME 검증 필요` 표시 |
| §6 비교표 | 주장 정직성 | 비교 시점 없음 | 대상 제품은 있으나 언제 기준인지 없음 | 조사 시점 명기, 없으면 표 삭제 |

## ③ 다음 한 수
1. 요약과 본문의 사례 수를 맞춘다 (blocking)
2. §3 "검증 완료" 문구를 치환한다
3. §5 임계값의 출처를 현업에 확인 요청한다
```

## 이 규칙의 근거

**만드는 쪽과 보는 쪽을 분리한 것.** 자기가 쓴 문장의 과장은 자기 눈에 보이지 않습니다.
쓸 때는 근거가 머릿속에 있어서 문장이 충분해 보이는데, 읽는 사람 머릿속에는 그 근거가 없습니다.
감사와 수정을 같은 세션에서 하면 스스로 고친 것을 스스로 통과시키므로, 세션 자체를 나눕니다.

**기계를 먼저 돌리는 것.** LLM에게 문서 전체를 주고 "문제를 찾아줘"라고 하면
LLM이 LLM 산출을 채점하는 순환에 빠집니다. 개수가 맞는지, 링크가 열리는지, 출처가 실재하는지는
판단이 아니라 확인입니다. 확인은 기계가 훨씬 정확하고 싸게 합니다.
대신 기계가 통과시킨 항목은 다시 감으로 판정하지 않습니다.
재판정을 허용하면 기계 검증의 의미가 사라집니다.

**도메인 수치를 직접 고치지 않는 것.** 등급·임계값 같은 도메인 수치는 문법적으로 완벽하면서
업계 기준으로는 틀릴 수 있습니다. 값 하나가 어긋나면 정상 건이 통째로 오탐됩니다.
그런데 모델은 그럴듯한 값을 아주 잘 만들어냅니다. 의심 표시까지가 에이전트의 일이고,
사실 판단은 전문가에게 넘깁니다. 고쳐주는 편이 친절해 보이지만, 틀린 값을 다른 틀린 값으로 바꾸는 셈입니다.

**근거 없는 주장을 지우지 않고 강등하는 것.** 지우면 다음 사람이 같은 주장을 다시 만듭니다.
"미확인"으로 남겨두면 그게 확인해야 할 목록이 됩니다.

**빠진 축을 묻는 것.** 과표현은 없는 말을 넣어서만 생기지 않습니다.
불리한 사실을 빼는 쪽이 더 흔하고, 더 잡기 어렵습니다. 있는 것만 검사하면 이걸 놓칩니다.
