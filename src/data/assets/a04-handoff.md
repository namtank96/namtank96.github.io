## 출력 예시

A구획에서 앵커가 있는 줄과 없는 줄의 차이:

```
❌  | 시각화 | 대시보드 개선함 | | |

✅  | 시각화 | 추세 그래프를 순수함수로 분리 | `trendPoly(series,{w,h,pad})`
                                              (renderDashboard 직전) | node 자체검증 통과 |
```

위쪽은 다음 세션이 대시보드 관련 파일을 전부 열어봐야 합니다. 아래쪽은 함수 하나만 열면 됩니다.

B구획에서 보류를 기록한 항목:

```
- **위젯 레지스트리** [M~L] — WIDGETS={id:{title,span,render}} 레지스트리 +
  순서 렌더 + add/remove
  - 선행: 없음
  - ⚠ 보류 권고 — 이유 둘. (1) 동작 중인 6개 섹션을 레지스트리로 재작성해야 해서
    회귀 위험이 실이득보다 큽니다. (2) add/remove 는 엔드유저 커스터마이즈인데
    요구가 확인된 적이 없는 투기적 기능입니다.
    사용자가 커스터마이즈를 명시 요청할 때 착수하세요.
    → 다음은 lineage 흐름(실가치·저위험)을 권장합니다.
```

이 항목을 그냥 지웠다면, 다음 세션이 똑같이 검토하고 똑같은 결론에 도달했을 겁니다.
보류 사유를 남기면 그 시간이 통째로 절약됩니다.

## 이 규칙의 근거

**왜 앵커를 강제하는가.** "무엇을 했다"는 서술은 다음 세션에게 아무것도 주지 않습니다.
결국 코드를 열어 찾아야 하고, 그게 재스코핑입니다. 파일명·함수명·식별자를 적으면
다음 세션은 그 지점으로 바로 점프합니다. **핸드오프의 값어치는 요약의 품질이 아니라 앵커의 정확도에서 나옵니다.**

**왜 단일 writer 경계를 파일 단위로 긋는가.** 작업 단위로 나누면("이 세션은 기능, 저 세션은 디자인")
둘 다 결국 같은 파일을 건드립니다. 기능 변경이 스타일을 건드리고 디자인 변경이 마크업을 건드리니까요.
파일 단위로 나누면 충돌 가능성이 구조적으로 0이 됩니다. 경계를 넘어야 하는 일이 생기면
그 세션에서 하지 않고 다음 세션 항목으로 넘깁니다.

**왜 규모를 강제하는가.** 규모가 없으면 다음 세션이 세션 끝 무렵에 여러 세션짜리 항목을
집어 들었다가 반쯤 하고 또 끊깁니다. 그러면 핸드오프가 한 겹 더 쌓입니다.
`S/M/L` 세 글자가 그걸 막습니다.

**왜 보류를 기록하는가.** 안 하기로 한 결정도 결정입니다. 지워버리면 다음 세션이
똑같이 검토하고 똑같이 보류합니다. 판단 비용을 두 번 내는 겁니다.
그리고 보류 사유는 나중에 상황이 바뀌었을 때 "이제 착수해도 되는가"를 판단하는 기준이 됩니다.

**왜 컨텍스트가 다 차기 전에 쓰는가.** 다 차고 나면 앵커를 확인할 여유가 없어서
기억으로 적게 됩니다. 기억으로 적은 앵커는 틀립니다. 그리고 틀린 앵커는
없는 앵커보다 나쁩니다 — 다음 세션이 그 자리를 찾다가 시간을 씁니다.
