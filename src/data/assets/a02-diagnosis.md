## 출력 예시

같은 항목이 미팅을 거치며 어떻게 바뀌는지가 이 포맷의 핵심입니다. 초도 미팅 직후:

```yaml
- id: it-01
  type: pain
  raw: "점검 결과가 여기저기 흩어져 있어서 매번 취합하느라 시간을 씁니다"
  interpretations:
    - at: 2026-08-10
      text: "데이터 사일로 → 통합 카탈로그 필요"
      basis: 웹서칭 + 업종패턴
      confidence: 낮음
      status: 현행
  verify: { method: 미팅질문, question: "취합은 어느 주기로, 누가 하시나요?", resolved: false }
```

2차 미팅에서 "취합"이 사일로 문제가 아니라 수작업 리포팅 문제였음이 드러난 뒤:

```yaml
- id: it-01
  type: pain
  raw: "점검 결과가 여기저기 흩어져 있어서 매번 취합하느라 시간을 씁니다"
  interpretations:
    - at: 2026-08-10
      text: "데이터 사일로 → 통합 카탈로그 필요"
      basis: 웹서칭 + 업종패턴
      confidence: 낮음
      status: 폐기
      retiredReason: "2차 미팅서 '취합'은 월말 수기 리포팅 문제로 확인. 저장소는 이미 단일."
    - at: 2026-08-24
      text: "월말 수기 집계 → 리포팅 자동화가 1차 니즈"
      basis: 2차 미팅 발언
      confidence: 높음
      status: 현행
  verify: { method: 미팅질문, question: "취합은 어느 주기로, 누가 하시나요?", resolved: true }
```

원문(`raw`)은 한 글자도 안 바뀌었고, 틀린 해석은 지워지지 않고 `retiredReason`과 함께 남았습니다.
석 달 뒤 "왜 통합 카탈로그 얘기를 접었더라"를 다시 묻지 않아도 됩니다.

## 이 규칙의 근거

**왜 원문을 다듬지 않는가.** 고객 발화를 정리해서 적어두면 두 달 뒤에 그게 고객 말인지 우리 해석인지 아무도 구분하지 못합니다.
그 상태에서 제안서를 쓰면 우리 추측이 고객 요구로 둔갑합니다. `raw`와 `interpretations`를 물리적으로 다른 필드에 두는 게
"주의해서 구분하자"보다 훨씬 확실합니다.

**왜 폐기 해석을 지우지 않는가.** 초기 해석은 웹서칭과 업종 패턴에 기대므로 자주 틀립니다.
틀린 것 자체는 문제가 아닌데, 지워버리면 같은 오해를 다음 건에서 또 합니다. `retiredReason`은 다음 건의 재료입니다.

**왜 행위자를 분리하는가.** 이 필드는 처음엔 없었습니다. 그런데 산출물을 만들 때 "대상이 같으면 하나로 묶는다"는
규칙 때문에, 실무자의 애로와 관리자의 요구가 대상만 같다는 이유로 한 화면에 뭉개졌습니다.
단순 누락이 아니라 이미 다른 규칙을 오염시키고 있었던 겁니다. **대상이 같아도 쓰는 사람이 다르면 다른 건입니다.**

**왜 갭을 저장하지 않는가.** 갭을 필드로 두면 현황이나 요구가 바뀔 때마다 갭을 손으로 갱신해야 하고, 반드시 어긋납니다.
계산으로 두면 어긋날 수가 없습니다. 그리고 대조 축이 "같은 대상의 현재 vs 목표"가 아니라
**"산출물이 요구하는 것 ↔ 현재가 제공하는 것"** 이라는 점이 중요합니다. 전자로 맞추려 하면
자료 명사와 업무 명사가 층위가 달라 짝이 안 맞습니다.

**왜 최소 입력을 페인 1건으로 낮췄는가.** 입력 요건이 무거우면 아무도 안 씁니다.
빈 칸을 막는 대신 가정 배지를 붙여 통과시키면, 그 배지 목록이 그대로 다음 미팅의 질문지가 됩니다.
못 채워서 시작을 못 하는 것보다 얕게 시작해 채워 나가는 게 낫습니다.
