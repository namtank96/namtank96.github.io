## 출력 예시

양쪽에 걸친 작업이 들어왔을 때:

```
요청: 새 화면 하나 만들어줘. 기능도 되고 디자인도 맞게.

분배:
  1. 구조 트랙 — 화면의 동작·데이터 흐름·상태를 먼저 정의합니다.
     (골격이 먼저입니다. 반대로 하면 시각을 다 잡은 뒤에 구조가 바뀌어 되돌아옵니다.)
  2. 표현 트랙 — 1의 결과 위에 토큰·레이아웃·컴포넌트를 얹습니다.

  충돌 시 우선순위: 표현 규칙은 표현 트랙이, 골격 규칙은 구조 트랙이 이깁니다.
  이번 건에서 부딪힐 지점은 상태 표시 방식 하나로 보입니다 —
  구조가 상태 3종을 요구하는데 표현 토큰에는 2종만 정의돼 있습니다.
  먼저 확인할까요, 아니면 구조 3종에 맞춰 토큰을 늘릴까요?

1번부터 시작합니다.
```

## 이 규칙의 근거

**골격이 먼저, 표현이 나중.** 순서를 안 정하면 매번 표현부터 하게 됩니다.
눈에 보이니까 진척이 실감 납니다. 그런데 표현을 다 잡은 뒤에 구조가 바뀌면
표현 작업이 통째로 날아갑니다. 반대 순서는 손해가 훨씬 작습니다.
구조 위에 표현을 얹는 것은 원래 예정된 작업입니다.

**충돌을 "둘 다 맞다"로 두지 않는 것.** 두 트랙이 같은 대상에 서로 다른 규칙을 가지면
반드시 부딪힙니다. 그때 우선순위가 없으면 그 자리에서 즉흥으로 정하고,
다음번에 또 다르게 정합니다. 영역으로 갈라두면 그 판단이 한 번으로 끝납니다.

**트랙을 셋 이하로 제한하는 것.** 넷이 되는 순간 이건 어느 트랙이지를 판단하는 데
드는 시간이 그냥 직접 부르는 시간보다 커집니다. 그러면 사용자가 분배자를 건너뜁니다.
건너뛰는 순간 공통 규율도 같이 건너뛰어집니다.

**공통 규율을 여기 두는 것.** 매 세션 같은 주의사항을 다시 설명하는 일이
에이전트를 여럿 쓸 때 가장 큰 낭비입니다. 트랙 공통인 것만 여기 모으고
트랙별 규칙은 각 트랙 문서에 두면 설명이 한 번으로 끝납니다.

**위임 도구가 없어도 멈추지 않는 것.** 환경에 따라 서브에이전트 호출이 안 되는 경우가 있습니다.
그때 분배할 수 없다는 말로 끝나면 이 에이전트는 반쪽입니다.
공통 규율을 적용해 직접 수행하는 경로를 열어두면 어디서든 작동합니다.
