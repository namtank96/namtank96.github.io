## 출력 예시

이 규칙이 실제로 하는 일은 "에이전트가 잘못된 방향으로 가려 할 때 스스로 멈추게 하는 것"입니다.
§1-6이 걸렸을 때의 전형적인 반응:

```
요청: 진단에 없는 내용인데 화면에 필요해 보여서 추가했습니다.

응답: §1-1 위반입니다. 입력에 없는 것을 산출물에 만들지 않습니다.
     선택지는 둘입니다.
     (a) 이 항목을 입력에 먼저 추가하고 근거·확신도를 답니다.
     (b) 규격이 이 경우를 못 담는 것이라면, 규격을 먼저 고칩니다(§1-6).
     산출물 쪽에서 우회하지 않습니다. 어느 쪽으로 갈까요?
```

§4 누락 점검 게이트를 돌렸을 때:

```
규격 확정 전 누락 점검 (5축)

  누가    ⚠  행위자 정의가 없습니다. 지금 구조로는 실무자의 애로와
             관리자의 요구가 대상만 같으면 한 건으로 묶입니다.
  무엇을  ✓  대상·산출물 정의됨
  왜      ⚠  성공 기준은 있으나 측정 지표가 없습니다.
  어떻게  ✓  흐름·분기 정의됨
  언제    ⚠  단계는 있으나 각 단계의 종료 조건이 없습니다.

  → 3개 축이 비었습니다. 확정 전에 채우거나, 비운 채로 간다는 결정을
    로그에 남기세요.
```

## 이 규칙의 근거

**왜 규격 전문을 여기 옮기지 않는가.** 운영 규칙 파일에 규격을 복사해두면 두 벌이 생기고, 반드시 어긋납니다.
어긋난 순간 어느 쪽이 진짜인지 아무도 모르게 됩니다. 그래서 이 파일에는 "매번 지켜야 할 것"만 두고
판단이 필요하면 원문을 읽게 합니다. **규칙이 규격과 어긋나면 규격이 이깁니다.**

**왜 결과가 아니라 규격을 고치는가.** 산출물 쪽에서 예외 처리로 우회하면 그 자리는 넘어가지만,
다음 건에서 같은 문제가 그대로 납니다. 규격을 고치면 그 뒤의 모든 건이 함께 고쳐집니다.
비용은 앞에서 한 번 더 내고, 이득은 계속 받습니다.

**왜 누락 점검 게이트가 따로 필요한가.** 결정 로그는 "무엇을 넣을까"만 기록합니다.
넣을지 말지 논의된 것은 남지만, **아예 논의되지 않은 축은 아무 흔적도 남지 않습니다.**
실제로 "누가 쓰는가"라는 축이 규격 v1.0에서 통째로 빠진 적이 있고, 단순 누락이 아니라
이미 다른 규칙을 오염시키고 있었습니다 — 대상이 같으면 하나로 묶는 규칙 때문에
서로 다른 사람의 요구가 한 화면에 뭉개졌습니다.

**왜 규격 1개마다 즉시 1건에 적용하는가.** 규격 4개를 쌓아두고 한꺼번에 검증하면
결함이 한꺼번에 쏟아지고, 어느 규격이 원인인지 분리되지 않습니다.
하나씩 적용하면 결함과 원인이 1:1로 붙습니다.

**왜 첫 건을 손으로 완주하기 전에 자동화하지 않는가.** 손으로 한 번 끝까지 가보기 전에는
어디가 반복이고 어디가 판단인지 알 수 없습니다. 그 상태에서 만든 자동화는
판단해야 할 곳을 자동화하고 반복을 남겨둡니다.
