  상상으로 채우게 되고, 정작 미팅에서 전제가 뒤집히면 시안을 통째로 버리게 됩니다.
  그렇다고 정보가 다 모일 때까지 기다리면 제안 일정이 안 나옵니다.
did:
  - 진단 스펙 → 도출 규칙 → 화면으로 이어지는 3단 사슬을 규격으로 정의
  - 진단 스펙을 JSON Schema 로 기계 검증 가능하게 만들고, 규격 문서와 항상 동기화
  - 업종 용어를 골격에서 분리해 도메인 어휘팩으로 교체 가능하게 설계
  - 형식 · 추적성 · 도메인 사실성 3층 검증 구조를 정의
judgment:
  - call: 갭을 저장 필드가 아니라 계산 결과로 두었습니다
    why: >-
      갭을 저장하면 현황이나 요구가 바뀔 때마다 손으로 갱신해야 하고, 반드시 어긋납니다.
      계산으로 두면 어긋날 수가 없습니다. 대조 축도 "같은 대상의 현재 대 목표"가 아니라
      "산출물이 요구하는 것 대 현재가 제공하는 것"으로 잡아야 짝이 맞습니다.
  - call: 최소 입력을 고객 페인 1건으로 낮췄습니다
    why: >-
      입력 요건이 무거우면 아무도 쓰지 않습니다. 빈 칸을 막는 대신 가정 배지를 붙여
      통과시키면, 그 배지 목록이 그대로 다음 미팅의 질문지가 됩니다.
  - call: 행위자를 별도 축으로 분리했습니다
    why: >-
      처음엔 없던 필드입니다. 그런데 "대상이 같으면 하나로 묶는다"는 규칙 때문에
      실무자의 애로와 관리자의 요구가 대상만 같다는 이유로 한 화면에 뭉개졌습니다.
      단순 누락이 아니라 이미 다른 규칙을 오염시키고 있었습니다.
result: >-
  페인 1건만 있어도 진단이 시작되고, 빈 곳은 가정 배지로 남아 다음 미팅의 질문지가 됩니다.
  추적성 없는 화면은 애초에 만들어지지 않습니다.
