situation: >-
  선제안 단계에서는 고객 정보가 부족합니다. 이 상태에서 화면 시안을 작성하면 근거 없는
  추정으로 내용을 채우게 되고, 미팅에서 전제가 뒤집히면 시안 전체를 폐기하게 됩니다.
  정보 확보까지 대기하면 제안 일정을 맞출 수 없습니다.
did:
  - 진단 스펙 → 도출 규칙 → 화면으로 이어지는 3단 사슬 규격 정의
  - 진단 스펙의 JSON Schema 기계 검증 체계 구축 및 규격 문서와 상시 동기화
  - 업종 용어를 골격에서 분리해 도메인 어휘팩으로 교체 가능하도록 설계
  - 형식 · 추적성 · 도메인 사실성 3층 검증 구조 정의
judgment:
  - call: 갭을 저장값이 아닌 계산값으로 정의
    why: >-
      갭을 저장하면 현황이나 요구가 바뀔 때마다 수동 갱신이 필요하고 불일치가 발생합니다.
      계산값은 어긋나지 않습니다. 대조 축은 "산출물이 요구하는 것"과 "현재가
      제공하는 것"으로 설정했습니다. 동일 대상의 현재와 목표를 비교하면 층위가 달라
      대응되지 않습니다.
  - call: 최소 입력을 고객 페인 1건으로 하향
    why: >-
      입력 요건이 무거우면 실사용이 발생하지 않습니다. 빈 칸을 차단하는 대신 가정 배지를
      부여해 통과시켰습니다. 이 배지 목록은 다음 미팅의 질문지로 사용됩니다.
  - call: 행위자를 별도 축으로 분리
    why: >-
      초기 규격에는 없던 필드입니다. "대상이 같으면 하나로 묶는다"는 규칙 때문에 실무자의
      애로와 관리자의 요구가 대상이 같다는 이유만으로 한 화면에 병합됐습니다. 누락에 그치지
      않고 다른 규칙까지 오염시키는 상태였습니다.
result: >-
  페인 1건으로 진단이 시작되며, 미확보 영역은 가정 배지로 남아 다음 미팅의 질문지가 됩니다.
  추적성이 확보되지 않은 화면은 생성되지 않습니다.
